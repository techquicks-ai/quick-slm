Quick SLM · documentation

Testing tool-calling at the 100M scale.

An educational post-mortem of an experimental 103M-parameter language model trained from scratch. The goal was to test if sub-billion parameter models can reliably read live context for tool calling. (Spoiler: They struggle, and this training run ended with negative results).

trained from scratcheducational recordnegative resultsopen, tested pipeline

The idea

Structure is cheap. Grounding is not.

The primary goal of this project was to test whether a very small model (100M parameters) could learn to emit syntactically valid JSON tool calls where the arguments depend on facts read out of context rather than recalled from weights. Most work on tool-using language models starts at the billion-parameter scale, and we wanted to push the capacity limits.

Quick SLM is built around that distinction. The prompt carries two separate blocks: <state>, injected by the server and authoritative, and <memory>, carried from earlier in the session and not. When the two disagree the state wins, and a whole category of training data exists to place them in conflict so that a model which guesses instead of reading can be caught doing it.

small on purpose

Small is the product, not a compromise. The target is the least capacity that can hold the behaviour.

trained from scratch

No base model is adapted. The corpus, the tokenizer and every checkpoint come from this pipeline.

reproducible

Every knob is typed configuration written into each checkpoint, and the whole test suite runs without a GPU.

Architecture

One decoder block, repeated

Quick SLM is a LLaMA-style decoder-only transformer: RMSNorm pre-normalisation, rotary position embeddings, SwiGLU feed-forward blocks, and grouped-query attention at 3:1. It uses an identical decoder block costing 3,540,096 parameters, repeated 24 times.

Below a billion parameters, deep and thin configurations outperform shallow and wide ones at a fixed budget, so depth is the axis these models spend on. Width has stayed at 576.

The configuration is not independently derived. It is the published SmolLM-135M configuration with two changes, and the parameter count decomposes exactly as the tied embedding, 24 identical blocks, and one final norm.

Training

From raw corpus to agent

A run is driven by numbered notebooks. They are deliberately thin: every piece of logic whose failure would be silent, the prompt template, the loss mask, the learning-rate schedule, the corpus ratios, lives in the framework behind a test. The notebooks mount storage, install the framework, and call into it.

Pretraining streams and filters public corpora into one interleaved binary: educational web text as the backbone, mathematics for argument correctness, and Python source, which is the closest signal there is to emitting a call with typed, nested arguments. Every stage is resumable, because the expensive ones are measured in days.

NEGATIVE RESULT: OPTIMIZER STEP TOO WIDE  Gradients were accumulated to 1,064,960 tokens before each step, which over a 10-billion-token budget permitted only 9,390 steps. Under Adam, the distance a parameter can travel is bounded by the sum of the learning rate over the schedule, and that sum came to just 1.53. Accumulation does not reduce arithmetic; it converts arithmetic into a wider batch, and past the point where the gradient estimate is already accurate enough, the same compute would have bought optimizer steps instead.

Tier-4 and above was chosen over strict tier-5 for the web text because strict filtering discarded 97 % of every byte streamed and projected a 24-day wall-clock against roughly three days. Mathematics kept the strict filter, because that corpus is small enough to afford it and argument correctness depends on it.

NEGATIVE RESULT: DATALOADER BUG  Although the budget was 10 billion tokens, a dataloader worker shuffling bug meant that the model actually saw only ~2.5B unique tokens exposed 4 times each. The effective batch size of unique sequences was drastically lower than planned.

NEGATIVE RESULT: FUNCTION CALLING AT PRETRAINING  2.5 % of the budget went on function-calling transcripts. Tool-call formatting then scored exactly zero at sixteen of the nineteen base checkpoints. The reason is the objective rather than the data: pretraining scores every token of a transcript equally, so the handful that make up a well-formed call carry no more weight than the boilerplate around them. Function-calling data should be moved entirely to fine-tuning.

Tool calling

Teaching the model to act

Supervised fine-tuning is where tool-calling is learned. The corpus is synthetic, generated by a Gemma 4 31B teacher, and organised into five categories that between them cover the ways a call can be right and the ways it can be wrong.

CategoryShareWhat it trains
single_stage40 %One request, one grounded call
multi_stage25 %Chains: a call, its result, the next call
state_memory_conflict20 %State and memory disagree; read the state
traps10 %Missing tool, missing argument, bad result
refusals5 %Out of scope; decline cleanly

Only the first stage spends teacher time. Raw teacher text is stored rather than a parsed verdict, so every filter tightened later re-applies for the cost of a processor-bound pass rather than another generation run.

Preferences

Collecting human judgement

Beyond fine-tuning, a small labelling service gathers the pairwise preference data that direct preference optimisation needs. It serves one scenario at a time and records which of two candidate responses a labeller prefers, to an append-only log.

The Paper

Structure Is Cheap, Grounding Is Not

THE PRIMARY NEGATIVE RESULT  Quick SLM 103M successfully acquired tool-call structure but comprehensively failed to ground its arguments in the injected state. When presented with counterfactual pairs (where only the state dictates the right argument), the model grounded both branches in only 4 of 44 cases (0/44 for the SmolLM2-135M control). Detailed analysis reveals the model was pattern-matching rather than genuinely reading state, showing that at the ~100M parameter scale, syntax and formatting are easily learned, but reliable contextual grounding is not.

The model was fine-tuned on 14.7M tokens of synthetic tool calling data. The evaluation separated grounded argument selection from surface imitation using counterfactual pairs.

Tool Calling & Grounding

The fine-tuned checkpoint emits well-formed calls for 99.9 % of inputs (vs. 2.4 % for the base model) and selects the correct tool 77.8 % of the time. However, as noted above, it failed at state grounding. Detailed error analysis shows these grounding failures divide between tool selection errors and arithmetic failures on read values, suggesting this failure stems from the corpus design or sub-135M scale.

Three Measurement Faults

The evaluation identified three measurement faults that corrupted initial results, highlighting the fragility of metrics at this scale:

  • Optimizer schedule: The optimizer step was too wide (accumulating over 1M tokens), reducing the parameter travel distance under Adam.
  • Data filter: Data filtering metrics obscured actual capacity limits.
  • Decoder: Calculation of hardware utilization was flawed (the 6N approximation and sparsity math produced an initial 148 TFLOPS vs the corrected 70.7 TFLOPS, halving the actual MFU).

Judge Self-Preference Bias

The evaluation exposed a 0.74-point self-preference bias caused by using the same Gemma 4 31B model for both corpus generation and evaluation. Rescoring with an independent judge isolated this bias.
